Overview

xoraya-cli is a Linux command-line tool for interacting with Xoraya / X2E dataloggers (ML-N4000 family and compatible devices). It replaces the Windows-only GUI workflow with a scriptable, headless interface suitable for automated data collection.

The tool is built in C++17, links directly against the X2E Linux SDK (libxorayasdk) installed as a system library, and produces no Qt dependency. The output binary is a single self-contained executable.

What it does

  • Discovers loggers on the local network via UDP broadcast
  • Lists measurements stored on a logger's HDD
  • Downloads measurements as MF4 files, split at 50 MB
  • Optionally deletes measurements from the logger after a successful download
  • Automates collection across multiple loggers, with optional looping
  • Applies an in-place post-processing fix to correct a DLC field bug in the Linux SDK

Command: download

xoraya-cli download <device> <dest_dir> [N] [--delete-after-download] [--stop-logging] [--last N] Download measurements to a local directory
ArgumentRequiredDescription
<device>YesLogger alias name or IP address
<dest_dir>YesLocal destination directory (created automatically)
NNoIndex of a specific measurement. Omit to download all. Mutually exclusive with --last.
--delete-after-downloadNoDelete each measurement from the logger immediately after it is successfully downloaded
--stop-loggingNoStop the logger's recording before downloading, restart it afterwards
--last <N>NoDownload only the N most recent measurements (N ≥ 1). Mutually exclusive with a specific index.

Examples

# Download all measurements (newest first)
./xoraya-cli download DX11252-2 /tmp/logs

# Download only the 3 most recent measurements
./xoraya-cli download DX11252-2 /tmp/logs --last 3

# Download measurement at index 7 only
./xoraya-cli download DX11252-2 /tmp/logs 7

# Download all, delete each one from the logger as it finishes
./xoraya-cli download DX11252-2 /tmp/logs --delete-after-download

# Download the 5 newest, delete each immediately, without interrupting recording
./xoraya-cli download DX11252-2 /tmp/logs --last 5 --delete-after-download --stop-logging

Newest first Measurements are always downloaded in reverse chronological order — the most recent measurement is transferred first. This ensures that the latest data is safe locally even if a download is interrupted.
Non-destructive by default --delete-after-download must be passed explicitly. Without it, no measurement is ever deleted from the logger. When the flag is set, each measurement is deleted individually right after its download and DLC-patch complete — logger storage is freed progressively, not in a batch at the end.
No deduplication Downloading the same measurement twice overwrites the existing file. Use --delete-after-download or the collect loop to avoid re-downloading already-collected data.

Command: delete

xoraya-cli delete <device> <N> Delete a measurement from the logger's HDD 
./xoraya-cli delete DX11252-2 2
⚠ Irreversible Use list to confirm the index before deleting. There is no undo.

Example output

⚠  Deleting measurement 2 from 'DX11252-2'...
   Measurement 2 deleted.

On Gen3 devices, deletion is performed by time range (begin/end timestamps of the measurement) via HddDeleteFinalMeasurement. On Gen2, it uses HddDeleteMeasurement with the measurement list object.

Command: collect

xoraya-cli collect [options] Automated multi-logger data collection

Combines scan + download into a single automated command. Can run once or loop indefinitely.

OptionDefaultDescription
--dest <dir>/home/Dexterlogs Destination directory (created if absent)
--delete-after-downloadoff Delete each measurement from the logger immediately after it is successfully downloaded
--interval <s>off Loop indefinitely, re-scanning every s seconds (must be > 0)
--device <ip>all Restrict to one logger by exact IP address
--dry-runoff Show what would happen without performing any transfer
--verboseoff Print full per-measurement progress (same output as download)
--stop-loggingoff Stop the logger's recording before download, restart it afterwards
--last <N>all Download only the N most recent measurements from each logger (N ≥ 1)
Newest first Like download, collect always transfers measurements in reverse chronological order. Combined with --last N, only the N most recent measurements per logger are downloaded.

Examples

# One-shot, all loggers (default dest: /home/Dexterlogs)
./xoraya-cli collect

# Target a specific directory
./xoraya-cli collect --dest /data/xoraya

# Loop every 5 minutes, delete after download
./xoraya-cli collect --dest /data/xoraya --interval 300 --delete-after-download

# Download only the 10 most recent measurements per logger
./xoraya-cli collect --last 10 --delete-after-download

# Restrict to one logger
./xoraya-cli collect --device 192.168.2.1 --dest /data/xoraya

# Preview without downloading
./xoraya-cli collect --dry-run --verbose

Output files & naming

Files produced by download and collect follow this scheme:

{logger_name}_{YYYYMMDD}_{HHmmss}-{YYYYMMDD}_{HHmmss}[_snapshot]_{NNNN}.mf4
PartFormatExample
logger_nameAlias from GetName() after connectionDX11252-2
start date/timeYYYYMMDD_HHmmss (UTC)20260423_130040
end date/timeYYYYMMDD_HHmmss (UTC)20260423_131920
_snapshotPresent only for Snapshot measurements_snapshot
_NNNN4-digit split counter (always present)_0001
extensionAlways .mf4 for Gen2.mf4

Examples

# Single-file measurement (still has _0001)
DX11252-2_20260423_130040-20260423_131920_0001.mf4

# 11-file split measurement
DX11252-2_20260423_130040-20260423_151210_0001.mf4
DX11252-2_20260423_130040-20260423_151210_0002.mf4
...
DX11252-2_20260423_130040-20260423_151210_0011.mf4

# Snapshot
DX11252-2_20260423_150000-20260423_150230_snapshot_0001.mf4

The split counter _0001 is always present, even for measurements that fit in a single file. This is standard WriterMf4 filter behavior. Splits occur at 50 MB (52 428 800 bytes).

Gen3 / DataCubeNSeries Gen3 downloads use engine::Copy (SelfOwned mode), which applies its own internal naming scheme. The CLI does not control Gen3 filenames.

Download flow (Gen2)

The Gen2 path uses HddGetMeasurement with a polling loop, mirroring the original Windows XorayaConnection::onDownloadEntries() logic. The sequence for each measurement:

HddDirMeasurement — read the measurement list from the logger HDD. enableShadow() is called to merge stream_queue and default_queue into a single measurement entry.

WriterMf4 filter created once — MsgFilterFactory::Create(WriterMf4) and attached to the LoggerDataRecv before the measurement loop. Properties: MaxFileSize=52428800, SplitOnMaxSize=true, Extension=mf4.

Per-measurement: update Filename — SetProperty("Filename", base_path) where base_path = dest_dir/logger_YYYYMMDD_HHmmss-YYYYMMDD_HHmmss. WriterMf4 appends _0001.mf4, _0002.mf4, etc.

HddGetMeasurement — ctrl->DoCmd(cmdGet) starts the transfer.

Polling loop (200 ms) — waits until both IsReceiving() == false (network transfer complete) and GetCnt(CId_IsDataConsuming) == 0 (FileWriterMdf has closed all files). g_abort is checked every iteration; if set, cmd::HddStop is sent.

callAgain() / finalizeShadow() — if cmdGet.callAgain() returns true, the transfer loop repeats from step 4 to fetch the next chunk (shadow segment). When it returns false and HasShadow() is true, finalizeShadow() is called.

DLC patch — patch_mf4_dlc() is called on every _NNNN.mf4 file in dest_dir matching this measurement's base filename. Files are loaded into memory, patched, and rewritten (see DLC section).

Per-measurement deletion — if --delete-after-download, delete_gen2() is called immediately after the DLC patch for that measurement. Logger storage is freed one measurement at a time rather than in a batch at the end.

Gen3 path

Gen3 devices use engine::Copy (SelfOwned mode). The CLI sets the target path and calls cp.Run() + cp.WaitForEndOfCopy(). Progress is reported via a CopyProgress callback. No DLC patch is applied to Gen3 files.

DLC bug & fix

Affected SDK: libxorayasdk 1.00.0046 All MF4 files produced by this SDK version have a zeroed DLC field in every fixed CAN bus-event record. The fix is applied automatically after each download.

The bug

libxorayasdk 1.00.0046's internal X2eToMdfConverter class writes 0x00 at byte 4 of CAN_DataFrame (the DLC_field read by the CAN viewer) for every fixed bus-event record. The correct DLC value is simultaneously written at byte 5 (flag2) by the same code path. VLSD records (the actual CAN payload data) are unaffected.

Fixed record layout

OffsetSizeFieldNote
0–12rec_idOne of {1, 3, 5, 7} for fixed CGs
2–98timestamp100 ns ticks since Unix epoch
101Asynchronousflag byte
11–144CAN_DataFrame[0..3]CAN ID bytes
151DLC_fieldBUG: always 0x00 ← patch target
161flag2correct DLC ← patch source
17–2913CAN_DataFrame[6..18]rest of frame

The fix — patch_mf4_dlc()

Implemented in downloader.cpp. Called automatically after every Gen2 measurement download, once CId_IsDataConsuming returns to zero (guaranteeing all MF4 files are closed).

Load the entire file into a std::vector<uint8_t>

Validate the file header: first 8 bytes must be "MDF     ". The MF4 ID block is the only block that does not carry a ## prefix — all other blocks (##HD, ##DG, ##CG, ##DT, ##DL) do.

Parse ##HD (always at offset 64) → ##DG chain; read dg_rec_id_size

Walk the CG chain; build a table: rec_id → {is_vlsd, data_bytes}

Skip DGs that contain no fixed CGs with rec_ids in {1, 3, 5, 7}

Collect DT payload spans (directly or via ##DL chain)

For each fixed record where buf[pos+15] == 0 and buf[pos+16] != 0: set buf[pos+15] = buf[pos+16]

If any patches were made: rewrite the full buffer to disk (single fwrite)

The condition byte4 == 0 && byte5 != 0 is intentional: it skips already-correct files (from the Windows SDK), CAN error frames (both bytes zero), and avoids overwriting a correct value. Running the patch on an already-patched file is safe and produces 0 patches.

Scale

A typical 50 MB split file from an 18-minute measurement contains ~1 233 995 fixed records. All have DLC_field = 0x00, all are patched. The patch runs in well under 1 second per file (in-memory sequential scan + single write).

Python validation tool

mf4_patch_dlc.py was used to confirm the hypothesis before C++ integration. It produces a patched copy (original untouched), validates MF4 structure, and spot-checks 500 patches. Useful for ad-hoc validation: 

python3 mf4_patch_dlc.py input.mf4 output_patched.mf4

Automation: systemd service

The repository ships a ready-to-use systemd unit that runs collect --interval --delete-after-download continuously from boot, re-scanning every 10 seconds (configurable).

Files

FilePurpose
xoraya-collect.conf.exampleCopy to xoraya-collect.conf and edit
xoraya-collect.servicesystemd unit — copy to /etc/systemd/system/
docs/install-service.mdFull installation instructions

Config file (xoraya-collect.conf)

# Destination directory for downloaded MF4 files
DEST=/home/Dexterlogs

# Re-scan interval in seconds (minimum 1)
INTERVAL=10

Edit this file with no sudo required. Changes take effect after sudo systemctl restart xoraya-collect.

Service unit (excerpt)

[Unit]
Description=Xoraya data collector
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=alexander
EnvironmentFile=/home/alexander/.../xoraya-collect.conf
ExecStart=/usr/local/bin/xoraya-cli collect \
          --dest ${DEST} --interval ${INTERVAL} --delete-after-download
Restart=on-failure
RestartSec=5

Installation (one-time)

Build and install the binary: make && sudo cp xoraya-cli /usr/local/bin/xoraya-cli

Create config: cp xoraya-collect.conf.example xoraya-collect.conf — edit DEST and INTERVAL

Install service: sudo cp xoraya-collect.service /etc/systemd/system/

Enable and start: sudo systemctl daemon-reload && sudo systemctl enable --now xoraya-collect

Troubleshooting

Connection errors

Connection failed / Error Connection/Invalid

CauseAction
Logger not reachableping <ip>
Previous session killed with SIGKILLWait 30–60 s for the SDK timeout to expire, then retry
Logger addressed by name after failed sessionTry by IP: ./xoraya-cli download 192.168.2.1 ...

Logger not found by scan

The scan uses UDP broadcast and cannot cross routers. The host and loggers must be on the same L2 subnet. Check firewall rules if they are on the same subnet but not responding.

Download errors

HddDirMeasurement failed

The SDK could not read the measurement directory. Check that the logger's HDD is accessible and that stop_logging_if_needed succeeded.

Download finished with state 3 (Abort)

State 3 is normal when Ctrl+C is pressed. If it appears without user intervention, it indicates a network interruption or logger reset during transfer.

Build errors
